User-run native read and fixed-marker write passed. Writing inserted 28 events without Enter, with the pending marker observed in 410 ms. This is manual evidence, not autonomous dot access. ## 1. Resolve the permitted dot execution route

First distinguish tool availability from implemented transport. Inspect the active dot tool surface and its applicable execution rules using metadata only. Determine whether an already supported terminal-specific route or supported computer-use runtime can address the intended terminal. Do not repeat completed installation research or try the manual native helper as a bypass.

Acceptance: record the exact callable tool/runtime and allowed action scope, or the exact missing capability. A local executable, working MCP stdio server or manual PASS alone does not satisfy this gate. If unavailable, limit subsequent work to contracts and fixtures until the capability is supplied. No additional permission is invented for already authorized local preparation. A missing tool cannot be fixed by asking for generic permission.

## 2. Prepare and verify the smallest safe product contract

Prepare a capability/status response and validate target/session binding, bounded snapshots, separate paste/submit, short-lived human enable, persistent operation identity, pause and unknown-outcome handling. Keep native dispatch unavailable unless phase 1 establishes a supported route. Reuse existing protections and tests; add only tests for changed behavior.

Acceptance in fixtures: stale or changed target/pane/focus/enable state rejects dispatch; pause blocks work not yet dispatched; overlapping writes and automatic retries are rejected; cancellation reports uncertainty after dispatch. Acceptance on a real terminal requires phase 1 and a coordinated synthetic test. Do not claim automatic detection of human typing or revocation of queued input. Native SendInput cannot provide atomic pane addressing; choose a route consistent with this limit rather than claiming that checks eliminate the race. Retargeting requires explicit human selection and validation and never clears a consumed attempt.

## 3. Coordinate one minimal OpenCode TUI test

Use the existing versioned minimal profile and an isolated synthetic workspace once the operation route is available. Before any AI prompt, agree on the exact harmless prompt, provider/model and bounded spend with the user. No provider-token expenditure is needed for planning or fixture work.

Acceptance: the user and agent observe the same identified terminal from launch, without manual attach; bounded read works; paste remains pending until separately authorized submit; one coordinated prompt completes; pause prevents the next queued action. No arbitrary windows or other active AI sessions are involved. A launch-only check and an actual provider completion must be reported separately.

## 4. Measure the demonstrated route

Record transport, snapshot, paste, submit and response timings separately. Report countdown time separately from tool latency. Record actual provider token usage/cost only if available; otherwise label it unavailable. Never infer token consumption from elapsed time or terminal character counts.

Acceptance: one small reproducible table with provenance, observed timings and available usage counters, distinguishing local/mock, manual and dot-connected runs. Agree on latency/spend targets before interpreting the measurements as a product pass. Avoid repeated provider calls merely for benchmarking.

## 5. Prepare the repository-to-consumer handoff

Prepare local reviewable changes and a pinned commit/artifact with a verification manifest. Publishing to GitHub remains a separate explicit action; do not retry a blocked push. Do not edit, launch or consume through the live ArtisanFeed project under the current scope.

Acceptance: identify the exact published commit/version and artifact hash, demonstrate isolated import/configuration against that pin, and document the proposed consumer changes without applying them. Live ArtisanFeed consumption requires a scope decision because the current instruction is not to touch it. No GitHub-to-ArtisanFeed integration is claimed from a local commit alone.
